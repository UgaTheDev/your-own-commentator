# Stream D (talk-back) friction

| Date | Tool / doc | What I was doing | What went wrong (exact error / link) | Time lost | Suggested fix |
|---|---|---|---|---|---|
| 2026-09-27 | boto3 / Bedrock | Streaming mic PCM into Nova 2 Sonic | boto3 has no `InvokeModelWithBidirectionalStream`; needs the experimental `aws-sdk-bedrock-runtime` (0.11.0, Python >= 3.12), a second AWS SDK in the same app | 10 min | Ship bidirectional streaming in boto3, or say so on the Sonic getting-started page |
| 2026-09-27 | Nova 2 Sonic getting-started ([sonic-getting-started](https://docs.aws.amazon.com/nova/latest/nova2-userguide/sonic-getting-started.html)) | Copying the Python sample | Sample imports `BedrockRuntimeClient` and builds `Config(...)`; 0.11.0 has `AsyncBedrockRuntimeClient` and raises `ConfigError: AsyncBedrockRuntimeConfig cannot be constructed directly. Use await AsyncBedrockRuntimeConfig.resolve(...) instead.` | 10 min | Pin the SDK version in the sample, or update it to `resolve()` |
| 2026-09-27 | aws-sdk-bedrock-runtime 0.11.0 | First bidirectional call | `UnsupportedTransportError: The configured transport (AIOHTTPClient) does not support duplex (bidirectional) event streaming ... Use a transport that does, such as smithy_http.aio.crt.AWSCRTHTTPClient.` The default install can't call the one operation it is needed for | 5 min | Default to CRT when the operation is duplex, or document `pip install aws-sdk-bedrock-runtime[awscrt]` + `transport=AWSCRTHTTPClient()` |
| 2026-09-27 | aws-sdk-bedrock-runtime credential chain | Using `aws login` credentials | With no explicit resolver the call hung for >90 s with no error (the chain has no `login` provider; the sample's `EnvironmentCredentialsResolver` needs `AWS_ACCESS_KEY_ID`) | 5 min | Support the `login` credential provider like boto3/CLI. Workaround used: a 10-line resolver that returns boto3's (auto-refreshing) frozen credentials in-process, nothing written to disk or env |
| 2026-09-27 | Nova 2 Sonic turn detection | Getting only the user transcript fast | Ending the audio content (`contentEnd`) right after speech never yields the USER transcript (our 20 s timeout fired); Sonic only transcribes after its endpointing sees trailing silence. Sending the silence at 4x real time cut ASR latency from ~0.65 s to ~0.35 s after end of speech | 15 min | Document that `contentEnd` does not force end-of-turn, or add an explicit "end of user turn" input event for push-to-talk clients |
| 2026-09-27 | Nova 2 Sonic output events doc | Parsing the ASR result | Doc shows `role` only on `contentStart`, but live events also carry `role` on `textOutput`, plus undocumented `userSpeechStart` / `userSpeechEnd` (`inputAudioOffsetMs`, `inputAudioDetectionOffsetMs`), and the USER `contentEnd` has `stopReason: "PARTIAL_TURN"` | 5 min | Add these events and fields to the output-events page |
| 2026-09-27 | aws-sdk-bedrock-runtime 0.11.0 + boto3 (pip) | Building the relay container (python:3.13-slim) from pipeline + talk requirements | `pip install` backtracked for minutes through every botocore release (1.40 down to 1.34) with no solution: `aws-sdk-bedrock-runtime[awscrt]` pulls `smithy-http[awscrt]` pinned to `awscrt~=0.32.0`, while `botocore[crt]` pins a different exact awscrt. The two AWS Python SDKs cannot share one CRT. Fix: drop `[crt]` in the image (it is only needed for `aws login` on a laptop) | 10 min | Align the awscrt pins across botocore and smithy-http, or loosen smithy-http to `>=0.32` |
| 2026-09-27 | Nova 2 Sonic bidirectional stream (cold) | First push-to-talk question after the relay starts | Cold first question: release to transcript 3.8 s (warm 0.35 s), release to answer audio 7.5 s (warm 2.3-3.8 s). The first HTTP/2 duplex CRT connection and stream setup dominate. Workaround: scale up and ask one warm-up question before the demo | 0 min (measured) | Document the cold-start cost, or offer a way to pre-open the connection |
